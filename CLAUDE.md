# CLAUDE.md

Rules for an agent working in this repo. Read this first.

## What this repo is

A gallery of 15 small Shiny apps whose screen is built in React. Each app
proves one thing that Shiny React makes possible and plain Shiny does not.
`catalog.yml` lists every app and is the only list.

This repo is not `shinyreact-apps`. That one ports existing bslib apps and has
a parity rule that bans Tailwind and shadcn. This one is greenfield and React
first, so the whole JavaScript ecosystem is in scope. Do not copy the parity
rules across.

## Words to use

This is the **ui.tsx pattern**. Never call it an SPA. The server does the data
work through `page_react()` and `reactive_output()`. A TSX client owns the
screen.

## The claim rule

Every app answers three lines, which live in `catalog.yml` and in the README of
the app:

```
Claim:        what this app can do
Plain Shiny:  what plain Shiny does instead, and why it is worse here
This app:     how this app does it
```

If you cannot fill in all three, stop and say so. The app does not make a
point, and a gallery of apps that make no point is the failure mode here.

A claim needs a number. Points rendered, frame time, rows filtered, round trips
avoided. Write down how you measured it. Four apps carry a Compare toggle that
renders the plain Shiny version beside the React one, which is the strongest
form of the same thing.

Two rules keep the apps small:

1. One screen per app. No tabs and no wizards. The gallery is the navigation.
2. No downloads at run time and no API keys. Each app ships its own small data
   file under `data/`, generated by a script in `tools/gen-data/`.

## The per-app contract

This is the decision everything else depends on. Read it before you write an
app.

Every app file produces a `server` function and a `ui`. The gallery composes
them. The `ReactApp()` or `shinyApp()` call at the bottom exists only so the
app runs on its own.

- Python resolves every path against `__file__`. `shiny run` does not change
  the working directory, and the gallery imports the module from the repo root.
- R resolves every path against `APP_DIR`, which the app sets itself when the
  gallery did not. Keep the `inherits = FALSE` guard. It stops one app from
  picking up another app's `APP_DIR`.
- Python apps use Shiny Core, not Express. Express gives the gallery no way to
  add the back link to the page.
- Name the Python logic module after the slug, for example `cell_atlas.py`.
  Never `logic.py`. The gallery loads every app into one `sys.modules`, so two
  apps with the same helper name would share whichever loaded first.
- Do not write a Vite config by hand. Copy `templates/app/vite.config.ts`. It
  leaves React out of the bundle so the app shares the React instance that owns
  the hooks. Two copies of React on one page makes every hook return nothing,
  and it reports no error.
- Read the hooks off `window.shinyreact` inside the component, not at module
  scope. That is what makes the component testable.

## Why the build output is committed

Posit Connect Cloud runs no Node at deploy time. Each app commits its
`www/ui.js` and `www/ui.css`, so a fresh clone runs with `shiny run` alone.
`npm run check-built` rebuilds every app and fails when the committed file does
not match the source. CI runs it on every pull request.

## Adding an app

```powershell
node tools/new-app.mjs <slug> "Title"
```

Then add a row to `catalog.yml` with all three claim fields, and run
`npm run catalog`. Do not edit the tables in README.md by hand.

## How I work

- Branch off `dev`. Name branches `feat/<name>`, `fix/<name>`, or
  `chore/<name>`. PR titles follow Conventional Commits.
- Commit in small batches. Show me the commit message and wait for approval.
- Format R with `air format .`. Format Python with `ruff format`.
- Run `prek install` once per clone. Run `prek run --all-files` before a PR.
- No em dashes anywhere. Not in code comments, not in commit messages, not in
  docs. Write plain and simple. No AI sounding phrases.
- Never commit `.env`, `.Renviron`, or any key. A pre-commit hook blocks the
  common names. Read a file before you stage it if it might hold a secret.
- `docs/local/` is git ignored. Plans, screenshots and scratch notes go there.

## Two traps that cost real time

Both were found by spiking against the installed packages, not guessed.

1. Mounted sub-apps never receive ASGI lifespan events. `App.on_shutdown()`
   registered inside an app never fires. Keep apps free of process level
   cleanup.
2. `/app/<slug>` with no trailing slash returns 404 rather than redirecting,
   because Shiny's own catch-all mount matches first. The gallery adds an
   explicit redirect route. Do not remove it.

## Commands

```powershell
# One app
shiny run apps/<slug>/app.py
Rscript --% -e "shiny::runApp('apps/<slug>', port = 3838)"

# The gallery
shiny run app.py
Rscript --% -e "shiny::runApp('.', port = 3838)"

# Build
npm run build -w apps/<slug>
npm run dev -w apps/<slug>
npm run check-built

# Tests
npx vitest run apps/<slug>
.venv/Scripts/python -m pytest apps/<slug>
Rscript --% -e "shiny::runTests('apps/<slug>', assert = TRUE)"

# Catalog and dependencies
npm run catalog
node tools/sync-requirements.mjs
```

R is not on the Bash PATH on this machine. Use PowerShell for `Rscript`, and
call `C:\Program Files\R\bin\Rscript.bat` when you need a full path. Passing
`-e` with a long expression through `Start-Process` mangles the quoting. Write
the R into a file under `docs/local/` and run that instead.
